This document records the evidence for an eventual INK 1.0. It is a running
record, not a readiness claim. Everything that does not depend on the production
soak is written here in final form. The soak-dependent parts (the soak-evidence
summary and the promote recommendation) are templates with numeric blanks, to be
filled from the soak ledger when the window closes.

The current state is: soak-independent evidence recorded; production-soak
evidence pending; Agent Card signature Phase C not started; no 1.0 readiness
claim.

This file is maintainer governance material and is intentionally kept outside
the published package (`governance/` is not in `package.json` `files`).

Marked values are recomputed from the repository by `npm run check:facts`, which
fails if the prose and the repository disagree.

## 1. Release-candidate readiness report

Every subsection below is soak-independent and is recorded in final form
against the release commit. Nothing here is a template.

### 1.1 1.0 scope

The 1.0 commitment is a freeze of the **mandatory base profile**: the
**15**[^ck] `base`-profile categories in the `ink.conformance.v1` corpus, carrying
**345**[^ck] vectors. They are:

`agent-card`, `agent-card-fetch`, `agent-card-signature`,
`authorization-header`, `connection-payload`, `first-contact-transcript`,
`jcs-number`, `jcs-string-safety`, `key-rotation`, `principal-normalization`,
`private-hostname`, `replay-freshness`, `signature-base`, `signed-body-utf8`
and `timestamp-validity`.[^ck]

They cover envelope structure, JCS number safety, signed-string surrogate
safety, raw-body UTF-8 validity, the Ed25519 signing base, the Authorization
header grammar, Agent Card schema, discovery fetch and card signature, the
connection and first-contact handshake payloads, key rotation authority,
timestamp grammar, replay freshness, principal normalization and the
private-hostname SSRF guard.

The base set is frozen by drift tripwires in `test/conformance-profile.test.ts`,
so a category cannot be added to or removed from `base` without a deliberate
edit to the frozen list. Nothing outside those 15[^ck] categories is a 1.0 base
requirement.

The vendor-neutral `network.ink.*` message namespace is the candidate 1.0 wire
namespace and is under evaluation through the soak. Receivers dual-accept it
alongside the legacy `network.tulpa.*` spelling, receiver-first and backward
compatible, as specified in `specs/ink-compatibility-policy.md`. The two audit
types whose detached signatures do not cover the envelope type stay
single-spelling and are documented as such.

### 1.3 Security review closure

INK has **not** undergone an independent third-party security audit. That
statement in `SECURITY.md`, `docs/maturity.md` and `docs/threat-model.md` is
current and MUST NOT be softened by anything in this record. What follows is the
closure record for two structured internal reviews. Both are closed.

**Review A, full library security audit (2026-06-10).** Multi-reviewer audit of
the published library across signature handling, canonicalization, key rotation,
replay protection, message-size and complexity bounds, SSRF defenses on the
agent-card fetch and the transparency-log verification path. Every
library-implementable finding was remediated and merged:

| Finding | Remediation | Commit |
|---------|-------------|--------|
| Ed25519 verified in permissive mode (small-order forgery) | RFC 8032 strict verification at every verify site (#53) | `a17f1e4` |
| Unbounded validation complexity, non-canonical JSON numbers | `validateMessage` complexity cap plus the JCS number profile (#54) | `ee915a2` |
| Prefix-dependent principal identity | canonical principal returned from `verifyInkAuth` (#55) | `ac55388` |
| Unbounded schema sizes | size bounds across card, audit, handshake and discovery schemas (#56) | `c98af10` |
| Inclusion cross-check consumed an unverified checkpoint | checkpoint signature verification plus origin binding (#57) | `6ad4ea0` |
| Inclusion proof trusted a caller-supplied event hash | proof verification bound to the receipt's event (#58) | `f66df6a` |
| Permissive Authorization header separators | single-space grammar, CR, LF and TAB rejected (#59) | `e315a0a` |
| Receipt not bound to the acknowledged message | `verifyReceipt` binds sender, recipient, message id and hash (#60) | `d15f6eb` |

Those eight shipped in `0.4.0`. The one finding deferred at the time, absence of
an RFC 6962 append-only consistency check (a `treeSize` comparison is not a
consistency proof, so split-view equivocation was undetectable), was closed by
`verifyConsistencyProof` (#62, `cb38310`) and the CLI cross-check (#63,
`7554160`), shipped in `0.5.0` (#64, `3d13d74`). No finding from review A remains
open.

**Review B, focused key, auth and encryption review (2026-06-22).** Independent
reviewers examined the key-rotation authority rule, the transport-auth path and
the ECIES encrypted-payload path. No critical or high cryptographic break was
found. Two remediations merged:

| Finding | Remediation | Commit |
|---------|-------------|--------|
| Retired keys accepted for live auth; replay TOCTOU on distributed nonce stores | `verifyInkAuth` requires an active key by default; atomic `addIfAbsent` nonce reservation (#122) | `84c4cf1` |
| Encryption AAD did not bind the recipient | AAD binds the recipient static key, recomputed locally on decrypt; recipient identity now required on decrypt (#123) | `7083bd1` |

Both shipped in `0.8.0`. A small number of low-severity observations were closed
as deliberate no-change and are recorded in the review threads. No finding from
review B remains open.

Neither review substitutes for an independent audit. Absence of a third-party
audit is carried forward as a known limitation in §1.7.

### 1.4 Package and release integrity and provenance

- The package is published as `@adastracomputing/ink`. The `conformance/`
  directory ships inside the published tarball with a subpath export, so an
  adopter installs the same corpus and manifest the reference is gated against.
- Releases are cut from GPG-signed tags through the `publish` workflow, which
  builds under the pinned Nix toolchain and publishes to npm with sigstore OIDC
  provenance. Each published tarball is traceable to the CI run that built it,
  and no long-lived npm publish credential exists in the pipeline.
- A `v<version>` tag publishes to `next`. A `latest-v<version>` tag re-cuts a
  soaked version as a patch and publishes it to `latest` under the same OIDC
  trusted-publisher identity, running the same build, test and packaging
  gauntlet, and additionally under the `npm-release` environment so environment
  protection rules apply to every move of `latest`.
- The tarball is smoke-tested by a pack-and-import check in CI on every push, so
  a broken-publish regression is caught before a release tag is cut.
- Reproducibility: `nix build` produces the tarball from a signed tag, so an
  adopter who does not trust the registry can rebuild and compare.
- Promotion to `latest` and any move to a 1.0 line remain a manual step behind
  an explicit human gate held by the lead maintainer. Nothing in this document
  authorizes either.

### 1.5 Compatibility policy statement

`specs/ink-compatibility-policy.md` is the normative contract and is not
advisory. For 1.0 the commitment is:

- The frozen base profile in §1.1 does not take a breaking change without a
  major version. A break is defined by the policy §2.1 and includes any change
  to the signature base, the canonicalization rules, the auth header grammar,
  the key-rotation authority rule or a closed enum.
- Backward-compatible additions land as minors under policy §2.2 and receivers
  support at least one prior minor across a stated transition window.
- Unknown fields are tolerated or rejected per surface, not globally. The
  `protocol` value is a closed per-surface enum, and intent types and receipt
  dispositions are closed enums.
- A second cryptographic suite arrives through a reserved top-level card member
  with receiver-first negotiation, per policy §2.4, so adding a suite is not a
  break.
- Deprecation and version sunset follow policy §6. There is no plan to drop
  `ink/0.1` within major 0.

Every wire change is reviewed against this policy before merge, as
`GOVERNANCE.md` requires.

### 1.7 Known limitations

Recorded plainly so a 1.0 claim cannot be read as more than it is.

- No independent third-party security audit. Two structured internal reviews are
  closed (§1.3); that is not equivalent.
- One production integrator. The soak evidence comes from a single deployment,
  so the traffic profile is one operator's, not the ecosystem's. Volume figures
  and their limitations are recorded in §3.
- The bus factor is one. The second-signer seat is open (§5).
- Browser use is feasible but not exercised by the maintainers.
- The encrypted-payload AAD composition may still evolve, consistent with the
  extension status of the `encryption` profile.
- Audit finality is not provided by the protocol alone; it depends on witness
  behavior, as `docs/threat-model.md` states.
- The delegation chain is a post-1.0 extension and carries no 1.0 stability
  commitment.

## 2. Soak exit criteria

These criteria are normative for a 1.0 cut. Meeting them is necessary. It is not
automatically sufficient: the lead maintainer still gates promotion.

### 2.0 The soak ledger

The criteria below are evaluated from a **soak ledger**, the evidence instrument
maintained by the production integrator. The ledger is the record of what was
observed on which day and under which deployed release. Its role here is
evidentiary only: this document states what each criterion requires the ledger
to show, and the ledger's storage, schema and operational mechanics are the
integrator's concern and live in the integrator's own repository.

Two rules govern the ledger's use throughout this section:

- **A day counts only if it is evidenced.** A day with no ledger entry is not a
  soak day.
- **There is no retroactive credit.** An unevidenced day cannot be reconstructed
  or backfilled after the fact. It is a gap, handled under §2.2.

### 2.1 Criterion 1: window

A production integrator MUST run the release under evaluation against real
inbound and outbound traffic for **60 evidenced days**, with no signature,
namespace or encrypted-path regressions.

The window is anchored at the **later** of:

1. the integrator's production deploy of the release under evaluation, and
2. the soak ledger going live in that integrator.

Both anchors MUST be recorded with a date and a deploy identifier before the
window can be considered started.

### 2.2 Resets, extensions and gaps

**An ink release adopted by the integrator resets the window** if the delta
between the previously soaked release and the adopted one either touches
published runtime code or changes any conformance vector's accept-or-reject
decision. Changes confined to documentation, tests, CI configuration and
conformance vectors that only extend coverage without altering an existing
decision do **not** reset the window. The reset determination MUST be recorded
with the two release identifiers and the reason.

**Integrator deploys do not reset the window.** The soak is meant to run under
real evolving conditions, and an integrator that cannot ship during the window
is not running a realistic soak.

**Coverage gaps.** A change that bypasses the ink inbound path or that breaks
soak instrumentation is a coverage gap, not a reset trigger in itself. It is
handled by length:

- A gap of **7 consecutive days or fewer** extends the window by the length of
  the gap.
- A gap of **more than 7 consecutive days** resets the window.

Gap start and end MUST both be recorded. An unevidenced day is a gap day.

**Incidents.** An incident on a soaked surface (signature verification,
namespace handling, the encrypted path or transport auth) that is attributable
to ink is a criterion-1 **failure**. The window resets from the production
deploy of the fix. An incident on a soaked surface that is **not** attributable
to ink does not reset the window, but its review MUST attach to the ledger, and
an incident whose attribution is unresolved at window close is treated as
attributable.

### 2.3 Criterion 2: evidenced behavior

The superseded version of this criterion asked for "no rise in rejection or
transport-auth-failure rates attributable to the release". It is **struck**. A
rate computed over near-zero traffic is vacuously green, and the house principle
carried over from the promotion gate is that absence of evidence is
`INSUFFICIENT_DATA`, not a pass. It is replaced by three evidenced parts, all of
which MUST hold.

**(a) Inbound blocks.** Zero release-attributable inbound blocks for known
peers. Every inbound block occurring in the window MUST be classified, and the
classification recorded. An unclassified block counts **against** the criterion.

**(b) Shadow census.** The nightly shadow census MUST return `GO`
continuously for the window. A `NO_GO` result is a criterion-2 failure. An
`INSUFFICIENT_DATA` result is a coverage gap and is handled under §2.2.

**(c) Attested synthetic exchange.** A daily attested synthetic exchange MUST
run in three variants covering the signature path, the namespace path and the
encrypted path. Across the window the completion rate MUST be at least **95%**,
with **zero** unexplained failures. A failure is "explained" only if its cause
is recorded and shown not to be release-attributable.

Organic traffic carries **no minimum volume requirement**. Exact organic counts
MUST be recorded rather than characterized, and if the volume is low that MUST
be stated as a limitation in plain terms in the soak-evidence summary rather
than smoothed into a rate.

An incomplete ledger, or a synthetic completion rate below the floor, at window
close yields `INSUFFICIENT_DATA` for this criterion. `INSUFFICIENT_DATA` is not
a pass: it extends the window until the evidence exists.

### 2.4 Criterion 3: corpus greenness over time

The conformance corpus and the `go-conformance` job MUST remain green on the
release commit for the duration, evidenced by a cadence rather than a single
run.

- **Weekly** re-run of the `go-conformance` job together with the TypeScript
  conformance and manifest-integrity suites, checked out at the pinned release
  tag and using pinned toolchain versions, so the run tests the corpus and not
  the surrounding ecosystem.
- **A final run at window close**, on the exact release commit.
- Each run MUST be recorded with its CI URL, date, commit and result.

A red re-run caused purely by environment decay (a disappeared toolchain
version, a registry outage, an expired action pin) is recorded and remediated
and does **not** reset the soak. The window nevertheless MUST NOT close until a
green run on the release commit has been re-established and recorded.

### 2.5 Phase C observation

Phase C does **not** get a fresh 60-day window. It gets a two-stage observation:

1. **At least 14 days in shadow**, with **zero** would-rejects of legitimate
   traffic. A would-reject of legitimate traffic restarts stage 1.
2. **At least 7 days enforced**, following stage 1.

Both stages MUST complete before a 1.0 cut may claim Phase C done. Either stage
MAY overlap the tail of the main soak window. Neither stage may start before the
Phase C floor of 2026-10-24, and the enforcement flip that begins stage 2 is an
owner decision under §5.

## 5. Owner decisions

Two items are owner decisions outside engineering's control:

- **The second-signer seat.** `GOVERNANCE.md` records the seat as open and the
  bus factor as one, and names that a 1.0 release blocker. Filling it requires
  nominating a person and having them hold an independent key. Engineering
  cannot produce that.
- **The freeze sign-off.** Committing to the frozen base profile is a governance
  act by the lead maintainer, not an outcome of green CI.

Nothing in the soak or in the Phase C staging waits on either. The soak window,
the evidence collection, the weekly conformance cadence and the Phase C shadow
stage all proceed independently and can complete with both items outstanding.

They gate exactly two acts:

1. the Phase C enforcement flip (the start of the §2.5 stage 2), and
2. the final promote or 1.0 cut.

If the second-signer seat is not filled by roughly mid-October 2026 it becomes
the critical path to 1.0: at that point the Phase C floor of 2026-10-24 and the
soak window are the only other constraints, and both are on track to clear
before an unfilled seat would.
